Vault sync links a Fireblocks workspace to CoinCover Control. Once it's linked, Control keeps its own record of every vault account and every wallet address in that workspace, and that record is what produces the **wallet derivation paths** returned inside a recovery package.

The two backup flows on the [Fireblocks partner guide](/partner-guides/fireblocks) protect the **keys**. Vault sync protects the **derivation paths** — the record of how each vault and address was derived, which is what's needed to rebuild the accounts once the keys are back.

It applies wherever CoinCover backs up a Fireblocks workspace: [Recover for Institutions](/institutional-recovery/overview) customers backing up their own workspace, and [wallet providers](/wallet-provider-recovery/overview) backing up their customers' on Fireblocks. It has no application to [retail recovery](/retail-recovery/overview), where there is no workspace to enumerate.

Vault sync is optional, and strongly recommended at onboarding.

## Why link it at onboarding

If the workspace was never linked, a recovery still returns your keys. It does not return the derivation paths — nothing in the package records how your accounts were derived, so you would need to export a vault report from Fireblocks at recovery time, or rebuild every account by hand.

A recovery is not something you get to repeat, and there is no way to add derivation paths to a package that has already been assembled. That is the whole argument for completing the link now rather than later.

## At a glance

|  |  |
| --- | --- |
| **Applies to** | Fireblocks workspaces backed up with CoinCover |
| **Who sets it up** | An organisation owner, in CoinCover Control. CoinCover is not involved |
| **Access needed** | A Fireblocks read-only (Viewer) API user, and its private key |
| **What CoinCover reads** | Vault accounts, the assets in each, and the addresses under them. Nothing else |
| **Refresh** | Once a day at a fixed time, plus on demand whenever you want it |
| **Where you receive it** | Inside a workspace recovery package, as a CSV alongside the key material |

<Note>
  Vault sync is set up and refreshed in CoinCover Control. There are no vault sync endpoints in the API reference — it isn't something you build against.
</Note>

## Before you start

You'll need three things in place:

- **A Fireblocks partner relationship with CoinCover, and a workspace backup against it.** Vault sync is reached from that backup's page in Control, and the controls only appear where the backup's partner is Fireblocks.
- **An Admin-level user in your Fireblocks workspace.** Creating an API user and uploading a CSR is an Admin-level action at Fireblocks. This is done at Fireblocks, not at CoinCover.
- **An organisation owner account in CoinCover Control.** Owners link and change workspace credentials. Every other user in your organisation holds the Member role — a Member can trigger a refresh and browse the synced vaults and addresses, but cannot link or change credentials. The permission is organisation-wide rather than per backup.

<Warning>
  The read-only API user is created in the **Fireblocks console**, not in CoinCover Control. You then paste the credentials Fireblocks issues into Control.
</Warning>

### What you'll make, and where each piece goes

Setup produces three things. It's easier to follow once you know where each one ends up.

| Item | What it is | Made where | Goes to |
| --- | --- | --- | --- |
| `api_user.csr` | A certificate signing request (CSR). It holds the public half of a new key pair, and is safe to share | On your own computer | The Fireblocks console, when you create the API user |
| `api_private.key` | The private half of that key pair. Treat it like a password | On your own computer, in the same step | CoinCover Control, pasted by an organisation owner |
| API key | An identifier Fireblocks issues for the API user, in the form `xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx` | The Fireblocks console | CoinCover Control, pasted alongside the private key |

<Tip>
  **Have the organisation owner do it, or be in the room.** Only an organisation owner can paste the credentials into Control, so the smoothest path is for the owner to generate the key pair on their own computer and link it straight away. If someone else generates it, the private key has to be handed to the owner. Don't send it by email or chat; use your password manager's secure sharing, and delete any copies once the workspace is linked.
</Tip>

## Set it up

<Steps>
  <Step title="Generate the key pair and CSR on your computer">
    Fireblocks issues the API key against a certificate signing request (CSR) that **you** generate, so the key pair originates on your own machine rather than at Fireblocks or at CoinCover. You do this once, with OpenSSL, before you open the Fireblocks console.

    <Tabs>
      <Tab title="Windows">
        1. Open **PowerShell** from the Start menu. Open it normally, **not** with _Run as administrator_. An administrator window starts in `C:\Windows\System32`, and your files would be saved there, where they're hard to find.
        2. Make a working folder and move into it:
           ```powershell
           mkdir -Force "$HOME\coincover-vault-sync"; cd "$HOME\coincover-vault-sync"
           ```
        3. Generate the key pair and CSR. Windows doesn't include OpenSSL, but Git for Windows does, so this calls it by its full path:
           ```powershell
           & "C:\Program Files\Git\usr\bin\openssl.exe" req -new -newkey rsa:4096 -nodes -keyout api_private.key -out api_user.csr -subj "/O=Your Organisation/CN=CoinCover Vault Sync"
           ```
           If you get _The term ... is not recognized_ or _cannot find the path_, Git for Windows isn't installed. Install it from [git-scm.com](https://git-scm.com/download/win), or run `winget install --id Git.Git -e`, then close and reopen PowerShell and run the command again. If `openssl version` already works in your PowerShell, you can use plain `openssl` instead of the full path.
        4. Open the folder so you can see both files:
           ```powershell
           explorer .
           ```
      </Tab>
      <Tab title="macOS and Linux">
        OpenSSL is already installed. Open **Terminal** and run:

        ```bash
        mkdir -p ~/coincover-vault-sync && cd ~/coincover-vault-sync
        openssl req -new -newkey rsa:4096 -nodes -keyout api_private.key -out api_user.csr -subj "/O=Your Organisation/CN=CoinCover Vault Sync"
        ```

        On macOS, `open .` opens the folder in Finder.
      </Tab>
    </Tabs>

    Replace `Your Organisation` with your company name if you like. The values are labels only, and nothing in Vault sync depends on them. Generating a 4096-bit key can take a few seconds, and prints a row of dots while it works.

    You now have two files in the folder: `api_user.csr`, which goes to Fireblocks, and `api_private.key`, which goes to Control and nowhere else.

    <Note>
      `-nodes` saves the private key without a passphrase. That's deliberate: Control only accepts an unencrypted key, one whose first line is `-----BEGIN PRIVATE KEY-----` or `-----BEGIN RSA PRIVATE KEY-----`.
    </Note>

    <Accordion title="OpenSSL is asking me questions (Country Name, State, ...)">
      You ran the command without the `-subj "..."` part, so OpenSSL is asking for the certificate fields one by one. You can answer them:

      - **Country Name** must be exactly **two letters**, such as `GB`, `US` or `CA`. Typing a full name like `Canada` makes OpenSSL stop with _Error making certificate request_. If that happens, run the command again.
      - For every other field, type `.` and press Enter to leave it blank.
      - Press Enter at **A challenge password** and **An optional company name** to skip them.
    </Accordion>

    Fireblocks documents this step at [Generate a CSR for an API user](https://developers.fireblocks.com/docs/generate-a-csr-for-an-api-user).
  </Step>
  <Step title="Create a read-only API user in Fireblocks">
    In the Fireblocks console, go to **Settings → Users** and select **Add user**, then choose **API user**.

    - **Name:** something recognisable, such as `CoinCover`.
    - **Role:** **Viewer**, the lowest-privilege role that can list vaults and addresses.
    - **CSR file:** upload `api_user.csr` from the folder you made in the previous step. Upload the `.csr` file, never the `.key` file.

    Select **Add user**. Fireblocks asks for owner approval before the API user goes live. Once it's approved, the user shows as **Active** in the users list.

    <Note>
      CoinCover reads nothing beyond vault accounts and addresses, but nothing at link time inspects the privilege level of the credentials you supply. Keeping the API user at Viewer is your control, not one CoinCover applies for you.
    </Note>
  </Step>
  <Step title="Copy the API key">
    In **Settings → Users**, find the API user you just created and use the copy control on its row to copy its **API key**. It's a 36-character identifier in the form `xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx`.
  </Step>
  <Step title="Link the workspace in CoinCover Control">
    An organisation owner opens the backup in Control (**Backups**, then **Manage** on the Fireblocks backup) and selects **Set up Vault Sync**.

    If you see a greyed-out **Awaiting Fireblocks credentials** button instead, you're signed in as a Member. Ask an organisation owner to do this step.

    In the dialog:

    - **Fireblocks API Key:** paste the API key you copied.
    - **Private CSR Key:** paste the **entire contents** of `api_private.key`, including the `-----BEGIN PRIVATE KEY-----` and `-----END PRIVATE KEY-----` lines. To copy the whole file without opening it, run this in the same folder:
      <CodeGroup>
      ```powershell Windows
      Get-Content -Raw api_private.key | Set-Clipboard
      ```
      ```bash macOS
      pbcopy < api_private.key
      ```
      </CodeGroup>

    Select **Link workspace**. Both values are encrypted on arrival and only the encrypted form is stored.
  </Step>
  <Step title="Let the first refresh run">
    Linking starts the first refresh automatically. It runs in the background, and the page follows it and updates itself when it finishes.
  </Step>
  <Step title="Confirm the refresh succeeded">
    Check the **refresh status and the refresh history**, not only that a refresh happened. Until a refresh has succeeded, there is nothing in the record to release at recovery.
  </Step>
  <Step title="Check the record looks right">
    Control lists your vault accounts with their asset and address counts, and you can open a single vault to see its addresses. Compare this against Fireblocks.

    This is the point to catch a workspace linked with credentials scoped to the wrong workspace — CoinCover cannot tell one of your workspaces from another, so any valid credentials will link and sync.
  </Step>
  <Step title="Tidy up the private key file">
    Once the first refresh has succeeded, you don't need `api_private.key` again. Delete it, or store it in your password manager. CoinCover can't give it back to you, and if it's ever lost you can issue a new API user at Fireblocks and link again.
  </Step>
</Steps>

### Troubleshooting setup

| What you see | What it means | What to do |
| --- | --- | --- |
| _'openssl' is not recognized_ (Windows) | OpenSSL isn't on your PATH | Use the full-path command in the Windows tab above |
| _Error making certificate request_ | A Country Name longer than two letters was typed at the prompt | Run the command again with `-subj`, or enter a two-letter code |
| You can't find `api_user.csr` | PowerShell was opened as administrator, so the files went to `C:\Windows\System32` | Run `explorer .` in the same window to open the folder they're in, or start again in a normal PowerShell window |
| OpenSSL asks for a _PEM pass phrase_ | `-nodes` was left off the command | Run the full command again. Control won't accept a passphrase-protected key |
| The Control button is greyed out and reads **Awaiting Fireblocks credentials** | You're a Member, not an organisation owner | An organisation owner links the workspace |
| _Must be an unencrypted PEM-encoded private key_ | The key is passphrase-protected, or the CSR was pasted instead of the key | Paste the contents of `api_private.key`, not `api_user.csr`. If the key starts with `-----BEGIN ENCRYPTED PRIVATE KEY-----`, generate a new pair with `-nodes` |
| _Private key appears truncated_ | The last line was missed when copying | Copy the whole file with the clipboard command above |
| _API key must be a valid UUID_ | Something other than the API key was pasted | Copy the API key from the API user's row in Fireblocks |

## Keeping it current

A refresh runs **automatically once a day, at a fixed time**. That time is set by CoinCover and is the same for every customer — there is no per-organisation cadence or window. You can also refresh **on demand** from Control at any time, as often as you like.

Refreshes run in the background. Having triggered one, the page updates itself with the vault and address counts when it completes. A large workspace can take longer than the page waits, in which case Control tells you to check back — reload it once the refresh has had time to finish.

Control shows the **recent refresh history** for your workspace, covering whether each was automatic or one you triggered, whether it succeeded, and how many vaults and addresses it found. Failures show the reason.

CoinCover's record is cumulative: it keeps everything it has ever seen in the workspace, including vaults and addresses you later delete at Fireblocks, so those still appear in the derivation paths returned at recovery. Allow for that if you reorganise.

## What CoinCover reads and stores

**Reads:** your vault accounts, the assets held in each, and the addresses under each asset. Nothing else — no balances, no transactions, no transfer history, no policies, no users. CoinCover cannot initiate any movement of assets, and you can revoke the API user at Fireblocks whenever you choose.

**Stores:** the vault accounts, with the identifier Fireblocks issued and the name you gave them there; the wallet addresses, with the asset, the address itself, its type, any tag and its index; the credentials you supplied, as ciphertext only; and one record per refresh showing whether it succeeded and how much it found.

The credentials cannot be read back. They're encrypted the moment they arrive and only the encrypted form is kept, so no screen, interface or CoinCover person can return them. If you've lost your own copy, issue a new API user at Fireblocks and link again.

## If you change or revoke credentials

Saving new credentials overwrites the stored pair, returns the workspace to pending, and the next refresh re-reads the whole workspace from scratch. Your previously synced vaults and addresses are retained throughout, so nothing is lost from what CoinCover holds.

Revoking the API user at Fireblocks does not remove anything from CoinCover. The record stays exactly as it was at the last successful refresh and continues to be used at recovery; it simply stops picking up anything new.

## What you get at recovery

Where the workspace has been synced, a [workspace recovery](/partner-guides/fireblocks#recovery) can return the derivation paths as a CSV alongside the key material — one row per address, giving the vault account and its name, the asset, the address, its type, any tag, and the hierarchical derivation path. The format is aligned to the Fireblocks Recovery Utility, so it can be imported rather than transcribed.
